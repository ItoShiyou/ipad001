## 問題設定

**両手が塞がる奏者（ギター、鍵盤、弦楽器）が、追加購入なしに、暗いステージで確実に譜めくりできること。**

フットスイッチ（AirTurn 等）は確実だが**購入が必要**であり、導入障壁になる。
一方で顔認識は「追加購入ゼロ」だが**暗所と誤発火に弱い**。
どちらか一方に賭けるのではなく、**複数方式を並べて実測で選ぶ。**

### 評価軸

| 軸 | 意味 |
|---|---|
| **購入** | 追加購入が不要か（多くの奏者が既に持っているか） |
| **暗所** | 暗転・スポット・逆光で動くか |
| **騒音** | 大音量バンド環境で動くか |
| **誤発火** | 意図しないめくりが起きにくいか ← **本番では最重要** |
| **両手** | 手を止めずに操作できるか |
| **実装** | 個人開発での実装難度 |

## 現時点の方針

**単一方式に賭けない。「複数の入力を同時に有効化でき、どれが来ても同じ動作をする」設計にする。**

```
入力層（複数同時に有効化可能）
├── タップ / スワイプ            … D3（常に有効。土台）
├── HIDキーボード                … フットスイッチ、BTリモコン
├── CoreMIDI                     … A1 / A4
├── ローカル直結リモート          … A2 / A3（Multipeer / BLE）
├── カメラ検出                    … B1 / B2（オプトイン、既定オフ）
├── モーション                    … C3（オプトイン、既定オフ）
└── タイムライン再生              … D1 / D2（オプトイン、既定オフ）
        ↓
   譜めくりイベント（統一） → 演奏ビュー
```

この構造にしておけば、**方式の採否を後から差し替えても製品の中核が揺れない。**
設計原則 P6（自動化は提案しかできない。人間の操作が常に勝つ）は全入力に適用する。

### 着手順の提案

| 順 | 対象 | 理由 |
|---|---|---|
| 1 | **D3**（広いタップ領域） | 実装が最も軽く、全員に効く |
| 2 | **HIDキーボード** | フットスイッチ所有者を即座にカバー |
| 3 | **A1（MIDI）** | ギタリストに追加購入ゼロで確実な手段。CoreMIDIは軽い |
| 4 | **A2（iPhoneリモート）** | 対象が最も広い。ローカル直結でサーバー不要 |
| 5 | **B1 / B2（カメラ）** | スパイク（SP-2〜SP-5）の結果次第。ここで初めて判断 |
| 6 | C3 / D1 / D2 | 以降 |

**カメラを最初にやらないのは、最も派手だが最も不確実だから。**
先に確実な手段を揃えておけば、カメラが実測で不合格でも製品は成立する。
